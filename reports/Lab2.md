# Отчёт по лабораторной работе № 2

## Тема и цель

Тема работы — серверное REST API для заявок студентов на заселение в общежитие. Цель — перенести хранение и обработку данных с браузера на сервер, сохранив модель студента и интерфейс первой лабораторной. Реализация выполнена на Python, Django и Django REST Framework (DRF).

## Что было в первой лабораторной и что добавлено во второй

Первая лабораторная содержит страницы со списком студентов, формой добавления и редактирования, карточкой студента, поиском и удалением. Её поля и сценарии работы использованы как основа второй лабораторной. Главная перемена: браузер больше не хранит записи самостоятельно. Он отправляет HTTP-запросы Django, а сервер проверяет данные и сохраняет их в `data/students.json`. Поэтому бизнес-правила действуют и при обращении к API напрямую, без формы.

Один студент представлен JSON-объектом:

```json
{
  "fullName": "Иванов Иван",
  "group": "M3301",
  "isuId": "262144",
  "dormitory": 8,
  "room": 512,
  "settlementDate": "2026-10-19",
  "isForeign": false,
  "notes": ""
}
```

Дата выше показывает только формат. Для создания записи нужна дата от дня запуска сервера до одного календарного месяца вперёд.

## Возможности приложения

На главной странице можно посмотреть список студентов, выполнить поиск по ФИО, группе или ИСУ ID и отфильтровать записи по группе, общежитию, комнате и признаку иностранного студента. Форма создаёт новую запись или загружает существующую для редактирования. В карточке показаны все поля студента. Удаление доступно из списка и карточки с повторным нажатием для подтверждения.

При открытии страницы JavaScript запрашивает данные с сервера. Файл `frontend/js/student-service.js` содержит все обращения к API через `fetch`; другие скрипты вызывают его функции и показывают результат. После добавления, изменения и удаления новый список снова загружается с сервера.

## Устройство серверной части

| Файл | Роль | Что объяснить на защите |
| --- | --- | --- |
| `dormitory_api/urls.py` | Маршруты | Связывает URL с обработчиками запросов. |
| `requests_api/views.py` | Контроллер | Получает HTTP-запрос, вызывает проверку и нужную операцию, возвращает JSON и статус. |
| `requests_api/serializers.py` | Валидация | Проверяет поля студента и фильтры; отклоняет неизвестные поля. |
| `requests_api/services.py` | Логика приложения | Ищет, фильтрует, создаёт, изменяет и удаляет студентов; следит за уникальностью ИСУ ID. |
| `requests_api/repository.py` | Хранение | Читает и записывает массив студентов в JSON-файле. |
| `requests_api/errors.py` | Обработка ошибок | Приводит ответы об ошибках к единому виду. |
| `requests_api/tests.py` | Проверка API | Проверяет основные действия и ошибки. |

Пример пути запроса: `POST /api/requests` попадает в `views.py`; сериализатор проверяет поля; `services.py` убеждается, что ИСУ ID свободен; `repository.py` сохраняет запись; контроллер возвращает созданный объект и `201 Created`. Это разделение соответствует схеме «контроллер → сервис → хранилище»: каждому файлу отведена одна понятная задача.

Хранилище — обычный JSON-массив, изначально `[]`. Чтение и запись выполняются под блокировкой, чтобы два запроса в **одном процессе** не изменили файл одновременно. Для демонстрации следует запускать один процесс Django.

## Маршруты API

| Метод | Путь | Действие | Успех |
| --- | --- | --- | --- |
| `GET` | `/api/requests` | Вернуть весь список или список с фильтрами | `200 OK` |
| `GET` | `/api/requests/{isuId}` | Найти одного студента | `200 OK` |
| `POST` | `/api/requests` | Создать студента | `201 Created` |
| `PATCH` | `/api/requests/{isuId}` | Изменить указанные поля | `200 OK` |
| `DELETE` | `/api/requests/{isuId}` | Удалить запись | `204 No Content` |
| `QUERY` | `/api/requests` | Фильтровать по JSON-объекту в теле запроса | `200 OK` |

`isuId` — шестизначный идентификатор студента. В URL он определяет конкретную запись. `PATCH` принимает только изменяемые поля, например `{"room":513}`; пустой объект не принимается. Страница редактирования для простоты отправляет все поля формы.

### Фильтрация

Для короткого запроса условия передаются в URL, например `GET /api/requests?group=M3301&dormitory=8`. Сервер проверяет значения и оставляет студентов, соответствующих **всем** указанным условиям. Доступны `group`, `isuId`, `dormitory`, `room`, `settlementDate`, `isForeign`, `fullName` и `q`. `fullName` ищется как часть ФИО без учёта регистра; `q` ищет по ФИО, группе и ИСУ ID. Остальные поля сравниваются точно. Интерфейс использует `GET`: в форме только несколько фильтров, поэтому URL остаётся коротким. API также поддерживает `QUERY` с теми же условиями в JSON-теле для большого набора фильтров. Его можно показать командой `curl` из раздела запуска.

### Проверка данных

| Поле | Правило |
| --- | --- |
| `fullName` | Фамилия и имя минимум из двух слов; буквы и дефис, до 120 символов. |
| `group` | Латинская заглавная буква и четыре цифры по шаблону `[A-Z][1-4][1-5][0-9]{2}`. |
| `isuId` | Шесть цифр, первая не ноль; значение должно быть уникальным. |
| `dormitory` | Целое число от 1 до 20. |
| `room` | Целое число от 100 до 599. |
| `settlementDate` | Дата в формате `ГГГГ-ММ-ДД`, от текущего дня до одного календарного месяца вперёд. Уже сохранённую прошедшую дату можно оставить без изменения при редактировании старой записи. |
| `isForeign` | Логическое значение `true`/`false`; если не передано при создании, используется `false`. |
| `notes` | Необязательный текст до 500 символов. |

Проверка в HTML-форме помогает пользователю сразу увидеть ошибку. Сервер повторяет проверку независимо от браузера: любой клиент может отправить запрос напрямую. При неверных полях API возвращает `422` и указывает конкретные ошибки.

### Коды и формат ошибок

| Код | Причина |
| --- | --- |
| `400` | Неверный формат запроса, например повреждённый JSON или пустой `PATCH`. |
| `404` | Студент или маршрут не найден. |
| `409` | Студент с таким ИСУ ID уже существует. |
| `422` | Поля или фильтры не прошли проверку. |
| `500` | Внутренняя ошибка сервера, например файл данных повреждён. |

Пример ответа об ошибке:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте поля запроса.",
    "details": {"isuId": ["Неверное значение."]}
  }
}
```

`details` показывает поле и причину ошибки; точный текст зависит от ошибки. `DELETE` при успехе возвращает `204` без тела ответа.

## Как запустить и показать работу

Из каталога `lab2`:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py runserver 127.0.0.1:8000
```

Открыть `http://127.0.0.1:8000/`. Для проверки API из другого окна терминала можно выполнить пример ниже. Дата берётся автоматически по часовому поясу сервера; ИСУ ID при повторном запуске примера нужно заменить на свободный.

```bash
TODAY=$(TZ=Europe/Moscow date +%F)
curl -i -X POST http://127.0.0.1:8000/api/requests \
  -H 'Content-Type: application/json' \
  -d "{\"fullName\":\"Иванов Иван\",\"group\":\"M3301\",\"isuId\":\"262144\",\"dormitory\":8,\"room\":512,\"settlementDate\":\"$TODAY\",\"isForeign\":false,\"notes\":\"\"}"
curl -i 'http://127.0.0.1:8000/api/requests?group=M3301&dormitory=8'
curl -i -X QUERY http://127.0.0.1:8000/api/requests \
  -H 'Content-Type: application/json' \
  -d '{"group":"M3301","isForeign":false}'
curl -i -X PATCH http://127.0.0.1:8000/api/requests/262144 \
  -H 'Content-Type: application/json' -d '{"room":513}'
curl -i http://127.0.0.1:8000/api/requests/262144
curl -i -X DELETE http://127.0.0.1:8000/api/requests/262144
```

Для демонстрации через интерфейс: добавить студента, найти его через поиск или фильтр, открыть карточку, изменить номер комнаты, затем удалить запись. После перезагрузки страницы сохранённые записи остаются в JSON-файле. Записи из cookie первой лабораторной автоматически в новый серверный файл не переносятся.

Запустить:

```bash
python manage.py check
python manage.py test requests_api
```

На момент подготовки отчёта проверка конфигурации прошла без замечаний, а три теста API завершились успешно. Тесты проверяют полный цикл создания, чтения, фильтрации, изменения и удаления; уникальность ИСУ ID и коды ошибок; дату и обработку повреждённого файла данных. ## Ответы на вопросы к защите

1. **Python в серверной веб-разработке.** Django получает HTTP-запрос, запускает Python-обработчик и отправляет ответ. Здесь обработчики в `requests_api/views.py` вызывают проверку и операции со студентами. Python выполняется на сервере, а JavaScript в `frontend/js/` — в браузере.

2. **FastAPI, Flask и Django REST Framework.** Flask даёт небольшой базовый набор для веб-сервера; остальное разработчик подбирает сам. FastAPI ориентирован на API и активно использует аннотации типов и Pydantic. DRF расширяет Django средствами для API: сериализаторами, классами представлений и JSON-ответами. В этой работе выбран DRF, что разрешено заданием.

3. **Типизация и аннотации типов в Python.** Python проверяет тип значения во время выполнения. Аннотация вроде `room: int` подсказывает ожидаемый тип человеку и инструментам, но сама по себе не проверяет HTTP-запрос. В проекте входные типы проверяют поля `StudentSerializer`: например, `dormitory` и `room` — целые числа, `isForeign` — логическое значение. Большинство функций проекта не используют аннотации типов.

4. **Модели данных: `dataclass`, Pydantic, словари и классы.** Студент после проверки представлен обычным словарём Python, а набор допустимых полей описан классом `StudentSerializer` в `serializers.py`. `dataclass` и Pydantic — другие способы описать структуру и правила данных; в этом проекте они не используются. Для JSON-файла достаточно словаря, который легко превращается в JSON.

5. **Исключения и их обработка.** При отсутствии студента сервис вызывает `NotFound`, при повторном ИСУ ID — `Conflict`, а неверные поля вызывают ошибку сериализатора. Обработчик в `errors.py` превращает эти исключения в JSON одного вида и ставит нужный HTTP-код. Неожиданная ошибка даёт `500`.

6. **Декораторы.** Декоратор оборачивает функцию и добавляет ей поведение; в веб-фреймворках им можно, например, пометить функцию как обработчик API. В этом проекте для API используются классы `APIView`, а пути связываются с ними в `dormitory_api/urls.py`. Декоратор для объявления маршрута здесь не нужен.

7. **Контекст запроса и область видимости данных.** В `views.py` объект `request` содержит метод, JSON-тело и query-параметры текущего запроса; path-параметр `isu_id` передаётся методу обработчика отдельно. Локальные переменные обработчика не сохраняются между запросами. Список студентов сохраняется в `data/students.json`; блокировка в `repository.py` общая для потоков одного процесса сервера.

8. **Синхронный и асинхронный код в Python.** Серверные методы `get`, `post`, `patch`, `delete` и `query` здесь обычные синхронные функции: операция завершается до отправки ответа. Асинхронные функции Python обычно объявляют через `async def` и используют `await`; в серверном коде этой работы их нет. Браузерный `fetch` использует `async/await` JavaScript — это другая среда выполнения.

9. **Итераторы, генераторы и коллекции.** Хранилище читает JSON-массив в список словарей. В `services.py` цикл `for` перебирает студентов при фильтрации, а `any(...)` проверяет совпадения через генераторное выражение, не создавая отдельный список проверок. Итерация позволяет обработать каждую запись по очереди.

10. **Модули, пакеты и слои.** Каждый `.py`-файл — модуль; каталоги `dormitory_api` и `requests_api` содержат модули приложения. `urls.py` объявляет пути, `views.py` обрабатывает HTTP, `services.py` содержит операции, `repository.py` читает и пишет данные. Благодаря такому разделению обработчик запроса не содержит код записи JSON-файла.

11. **REST и RESTful API.** Ресурс в этой работе — запись студента: весь список доступен по `/api/requests`, одна запись — по `/api/requests/{isuId}`. Метод сообщает действие над ресурсом, а ответ содержит JSON и статус. Такой подход называют RESTful. Дополнительный метод `QUERY` реализован потому, что он прямо указан в задании.

12. **HTTP-методы и коды состояния.** `GET` читает (`200`), `POST` создаёт (`201`), `PATCH` изменяет (`200`), `DELETE` удаляет (`204` без тела), `QUERY` фильтрует (`200`). Ошибки: `400` — некорректный запрос, `404` — нет записи или пути, `409` — ИСУ ID занят, `422` — неверные поля, `500` — ошибка сервера.

13. **Маршрутизация, path- и query-параметры.** `urls.py` направляет запрос к нужному обработчику. В пути `/api/requests/262144` число `262144` — `isuId` нужного студента. В `/api/requests?group=M3301&dormitory=8` значения после `?` — query-параметры фильтра, которые читает `request.query_params`. Они не обозначают отдельного студента.

14. **JSON, сериализация и десериализация.** JSON передаёт объекты и массивы в текстовом формате. DRF разбирает JSON-тело запроса в значения Python и формирует JSON-ответ из результата обработчика. Для файла `repository.py` использует `json.load` при чтении и `json.dumps` при сохранении.

15. **Серверная валидация и ошибки.** `StudentSerializer` проверяет поля при создании и изменении, `FilterSerializer` — параметры фильтра. Например, ИСУ ID должен состоять из шести цифр, а дата заселения должна попасть в разрешённый интервал. HTML-форма тоже подсказывает ограничения, но прямой запрос может обойти её; поэтому окончательное решение принимает сервер. Ошибки полей приходят с `422` в общем формате `error`.

16. **Stateless-архитектура.** Сервер не хранит в сессии браузера «текущего студента» или «текущий фильтр»: каждый запрос содержит нужный ID, поля или условия фильтрации. Файл JSON хранит сами записи, и это не мешает stateless-подходу к обработке запросов. Во второй лабораторной браузер не сохраняет список студентов в cookie.

17. **Хранение и фильтрация в памяти и JSON-файле.** `repository.py` читает JSON-файл в список Python и записывает обновлённый список обратно. `services.py` перебирает записи и оставляет те, которые отвечают всем заданным условиям. Для небольшого учебного набора данных этого достаточно; проект запускается одним процессом Django.

18. **CRUD и уникальная идентификация ресурса.** CRUD — создание (`POST`), чтение (`GET`), изменение (`PATCH`) и удаление (`DELETE`). ИСУ ID служит ключом записи в URL. При создании и изменении `services.py` проверяет, что другой студент не использует такой ID, иначе отвечает `409`.

**Как показать `QUERY` на защите.** Веб-форма использует `GET` для своего небольшого набора фильтров. Серверный `QUERY` принимает условия в JSON-теле; пример команды `curl -X QUERY` приведён выше. Результат фильтрации у обоих методов одинаковый.
