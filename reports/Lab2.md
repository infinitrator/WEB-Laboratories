# Отчёт по лабораторной работе № 2

## Тема и цель

Тема работы — серверное REST API для заявок студентов на заселение в общежитие. Цель — перенести хранение и обработку данных с браузера на сервер, сохранив модель студента и интерфейс первой лабораторной. Реализация выполнена на Python, Django и Django REST Framework (DRF).

## Что было в первой лабораторной и что добавлено во второй

Первая лабораторная содержит страницы со списком студентов, формой добавления и редактирования, карточкой студента, поиском и удалением. Её поля и сценарии работы использованы как основа второй лабораторной. Главная перемена: браузер больше не хранит записи самостоятельно. Он отправляет HTTP-запросы Django, а сервер проверяет данные и сохраняет их в `data/students.json`. Поэтому бизнес-правила действуют и при обращении к API напрямую, без формы.

Один студент представлен JSON-объектом:

```json
{
  "fullName": "Иванов Иван",
  "group": "M3301",
  "isuId": "262144",
  "dormitory": 8,
  "room": 512,
  "settlementDate": "2026-10-19",
  "isForeign": false,
  "notes": ""
}
```

Дата выше показывает только формат. Для создания записи нужна дата от дня запуска сервера до одного календарного месяца вперёд.

## Возможности приложения

На главной странице можно посмотреть список студентов, выполнить поиск по ФИО, группе или ИСУ ID и отфильтровать записи по группе, общежитию, комнате и признаку иностранного студента. Форма создаёт новую запись или загружает существующую для редактирования. В карточке показаны все поля студента. Удаление доступно из списка и карточки с повторным нажатием для подтверждения.

При открытии страницы JavaScript запрашивает данные с сервера. Файл `frontend/js/student-service.js` содержит все обращения к API через `fetch`; другие скрипты вызывают его функции и показывают результат. После добавления, изменения и удаления новый список снова загружается с сервера.

## Устройство серверной части

| Файл | Роль | Что объяснить на защите |
| --- | --- | --- |
| `dormitory_api/urls.py` | Маршруты | Связывает URL с обработчиками запросов. |
| `requests_api/views.py` | Контроллер | Получает HTTP-запрос, вызывает проверку и нужную операцию, возвращает JSON и статус. |
| `requests_api/serializers.py` | Валидация | Проверяет поля студента и фильтры; отклоняет неизвестные поля. |
| `requests_api/services.py` | Логика приложения | Ищет, фильтрует, создаёт, изменяет и удаляет студентов; следит за уникальностью ИСУ ID. |
| `requests_api/repository.py` | Хранение | Читает и записывает массив студентов в JSON-файле. |
| `requests_api/errors.py` | Обработка ошибок | Приводит ответы об ошибках к единому виду. |
| `requests_api/tests.py` | Проверка API | Проверяет основные действия и ошибки. |

Пример пути запроса: `POST /api/requests` попадает в `views.py`; сериализатор проверяет поля; `services.py` убеждается, что ИСУ ID свободен; `repository.py` сохраняет запись; контроллер возвращает созданный объект и `201 Created`. Это разделение соответствует схеме «контроллер → сервис → хранилище»: каждому файлу отведена одна понятная задача.

Хранилище — обычный JSON-массив, изначально `[]`. Чтение и запись выполняются под блокировкой, чтобы два запроса в **одном процессе** не изменили файл одновременно. Для демонстрации следует запускать один процесс Django.

## Маршруты API

| Метод | Путь | Действие | Успех |
| --- | --- | --- | --- |
| `GET` | `/api/requests` | Вернуть весь список или список с фильтрами | `200 OK` |
| `GET` | `/api/requests/{isuId}` | Найти одного студента | `200 OK` |
| `POST` | `/api/requests` | Создать студента | `201 Created` |
| `PATCH` | `/api/requests/{isuId}` | Изменить указанные поля | `200 OK` |
| `DELETE` | `/api/requests/{isuId}` | Удалить запись | `204 No Content` |
| `QUERY` | `/api/requests` | Фильтровать по JSON-объекту в теле запроса | `200 OK` |

`isuId` — шестизначный идентификатор студента. В URL он определяет конкретную запись. `PATCH` принимает только изменяемые поля, например `{"room":513}`; пустой объект не принимается. Страница редактирования для простоты отправляет все поля формы.

### Фильтрация

Для короткого запроса условия передаются в URL, например `GET /api/requests?group=M3301&dormitory=8`. Сервер проверяет значения и оставляет студентов, соответствующих **всем** указанным условиям. Доступны `group`, `isuId`, `dormitory`, `room`, `settlementDate`, `isForeign`, `fullName` и `q`. `fullName` ищется как часть ФИО без учёта регистра; `q` ищет по ФИО, группе и ИСУ ID. Остальные поля сравниваются точно. `QUERY` применяет ту же логику, но условия передаются JSON-объектом в теле запроса, что удобно при большом числе фильтров.

### Проверка данных

| Поле | Правило |
| --- | --- |
| `fullName` | Фамилия и имя минимум из двух слов; буквы и дефис, до 120 символов. |
| `group` | Латинская заглавная буква и четыре цифры по шаблону `[A-Z][1-4][1-5][0-9]{2}`. |
| `isuId` | Шесть цифр, первая не ноль; значение должно быть уникальным. |
| `dormitory` | Целое число от 1 до 20. |
| `room` | Целое число от 100 до 599. |
| `settlementDate` | Дата в формате `ГГГГ-ММ-ДД`, от текущего дня до одного календарного месяца вперёд. Уже сохранённую прошедшую дату можно оставить без изменения при редактировании старой записи. |
| `isForeign` | Логическое значение `true`/`false`; если не передано при создании, используется `false`. |
| `notes` | Необязательный текст до 500 символов. |

Проверка в HTML-форме помогает пользователю сразу увидеть ошибку. Сервер повторяет проверку независимо от браузера: любой клиент может отправить запрос напрямую. При неверных полях API возвращает `422` и указывает конкретные ошибки.

### Коды и формат ошибок

| Код | Причина |
| --- | --- |
| `400` | Неверный формат запроса, например повреждённый JSON или пустой `PATCH`. |
| `404` | Студент или маршрут не найден. |
| `409` | Студент с таким ИСУ ID уже существует. |
| `422` | Поля или фильтры не прошли проверку. |
| `500` | Внутренняя ошибка сервера, например файл данных повреждён. |

Пример ответа об ошибке:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте поля запроса.",
    "details": {"isuId": ["Неверное значение."]}
  }
}
```

`details` показывает поле и причину ошибки; точный текст зависит от ошибки. `DELETE` при успехе возвращает `204` без тела ответа.

## Как запустить и показать работу

Из каталога `lab2`:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py runserver 127.0.0.1:8000
```

Открыть `http://127.0.0.1:8000/`. Для проверки API из другого окна терминала можно выполнить пример ниже. Дата берётся автоматически по часовому поясу сервера; ИСУ ID при повторном запуске примера нужно заменить на свободный.

```bash
TODAY=$(TZ=Europe/Moscow date +%F)
curl -i -X POST http://127.0.0.1:8000/api/requests \
  -H 'Content-Type: application/json' \
  -d "{\"fullName\":\"Иванов Иван\",\"group\":\"M3301\",\"isuId\":\"262144\",\"dormitory\":8,\"room\":512,\"settlementDate\":\"$TODAY\",\"isForeign\":false,\"notes\":\"\"}"
curl -i 'http://127.0.0.1:8000/api/requests?group=M3301&dormitory=8'
curl -i -X QUERY http://127.0.0.1:8000/api/requests \
  -H 'Content-Type: application/json' \
  -d '{"group":"M3301","isForeign":false}'
curl -i -X PATCH http://127.0.0.1:8000/api/requests/262144 \
  -H 'Content-Type: application/json' -d '{"room":513}'
curl -i http://127.0.0.1:8000/api/requests/262144
curl -i -X DELETE http://127.0.0.1:8000/api/requests/262144
```

Для демонстрации через интерфейс: добавить студента, найти его через поиск или фильтр, открыть карточку, изменить номер комнаты, затем удалить запись. После перезагрузки страницы сохранённые записи остаются в JSON-файле. Записи из cookie первой лабораторной автоматически в новый серверный файл не переносятся.

## Проверка результата

Запустить:

```bash
python manage.py check
python manage.py test requests_api
```

На момент подготовки отчёта проверка конфигурации прошла без замечаний, а три теста API завершились успешно. Тесты проверяют полный цикл создания, чтения, фильтрации, изменения и удаления; уникальность ИСУ ID и коды ошибок; дату и обработку повреждённого файла данных. Тесты используют временный файл, поэтому демонстрационный `data/students.json` не меняется.

## Краткие ответы для защиты

**Почему сервер, если форма уже проверяет ввод?** Проверку формы можно обойти прямым HTTP-запросом. Сервер должен самостоятельно защищать данные.

**Что означает REST в этой работе?** Ресурс студента доступен по URL, а действие задаётся методом HTTP: `GET`, `POST`, `PATCH` или `DELETE`. Сервер возвращает JSON и подходящий статус.

**Зачем ИСУ ID в адресе?** Он однозначно определяет студента для чтения, изменения и удаления. При создании дубликат отклоняется с `409`.

**Чем отличаются `GET` с параметрами и `QUERY`?** Результат фильтрации одинаковый; у `GET` условия в URL, у `QUERY` — в JSON-теле.

**Почему несколько файлов на сервере?** Маршруты, HTTP-обработка, правила и запись файла имеют разные задачи. Это позволяет менять интерфейс или способ хранения без переписывания всех частей сразу.

**Где сохраняются данные?** В `data/students.json` в виде массива JSON-объектов. Приложение рассчитано на учебный локальный запуск одним процессом.

**Почему при удалении код `204`?** Операция выполнена, но возвращать объект уже нечего.
